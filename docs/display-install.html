Hangar display — install

Wiring + software cheat-sheet for the 3.2" ILI9341 SPI display on pi.vpn. Check off each step as you go — progress is saved in this browser.

Parts check

Power down before wiring

Important: shut the Pi cleanly before wiring. The Pi's GPIO is not hot-pluggable, and a wiring slip with the Pi powered can fry both ends.

Wiring

Pi Zero W 40-pin header. All connections use 3.3V logic and 3V3 power — do not wire VCC to the Pi's 5V rail even though the display says it accepts 5V.

Display pinPi BCMPi header pinNotes
VCC3V317Power. Use 3V3, not 5V. Shares pin 17 with LED — see note below.
GNDGND6Any GND pin works (6/9/14/20/25/30/34/39).
CSBCM 824SPI0 CE0 — display chip select.
RESETBCM 2522Display reset, driven by luma.lcd at init.
DCBCM 2418Data / command select.
SDI / MOSIBCM 1019SPI MOSI. Shared with the touch chip.
SCKBCM 1123SPI clock. Shared with the touch chip.
SDO / MISOBCM 921SPI MISO. Needed by the touch chip (display alone wouldn't need it).
T_CSBCM 726SPI0 CE1 — touch chip select. Distinct from CS / BCM 8.
LED3V317Backlight, always-on. Shares pin 17 with VCC — see note below.
Pin 1 is occupied by the DS18B20 temp probe, so VCC + LED both share pin 17 (the Pi's other 3V3 pin). Three ways to land two wires on one pin:
  1. Bridge on the display side (cleanest if you have a male-male jumper or scrap of solid wire): one F-F jumper from Pi pin 17 → display VCC, then a short male-male jumper between the display's VCC and LED pins.
  2. Y-pigtail / breadboard: distribute pin 17 through a tiny breadboard rail, run separate jumpers from the rail to VCC and to LED.
  3. Pigtail off the temp probe: only works if the existing pin-1 connector accepts a stacked second jumper (most Dupont housings don't). Usually impractical.

The other touch pins on the display (T_CLK, T_DIN, T_DO, T_IRQ) are left unconnected: T_CLK/T_DIN/T_DO are internally shared with the display's SPI bus on this PCB, and T_IRQ is optional (the driver polls instead).

Tip: use consistent jumper colors so you can trace at a glance — red = 3V3, black = GND, anything else for signals. Verify each jumper end-to-end with a continuity test (or just gently tug) before powering on.

Enable SPI

The Pi's SPI peripheral is off by default. luma.lcd won't work without it.

Install luma.lcd

Dry-run sanity check (no SPI write)

Before driving the panel, confirm state-read + render work standalone.

First light — drive the panel

If the display stays blank: check power continuity (multimeter across VCC/GND should read 3.3V), check that raspi-gpio get 8 24 25 shows OUTPUT on those pins after running the script, check the journal for SPI errors with dmesg | tail -20.
If text is sideways or mirrored: the rotate= argument in display_loop.py needs adjusting. Try rotate=0, 2, or 3 until orientation matches the mockup.
If colors are swapped (red↔blue): the panel is using BGR ordering instead of RGB. luma.lcd can be told via bgr=True on the ili9341() constructor — add that and re-test.

Enable the service

Configure the FlashAir SSID pattern (optional)

The renderer colors a matching SSID as amber ("active") and others as grey ("steady state"). Default pattern is flashair. Override in .env:

echo 'FLASHAIR_SSID_PATTERN=flashair' | sudo tee -a /usr/lib/cgi-bin/remote-switch/.env

Touch calibration

The XPT2046 returns raw 12-bit values that need to be mapped to screen pixels. Defaults in touch.py work for "most" 3.2" MSP3218 panels, but every panel drifts a bit — tap-the-button accuracy improves a lot after a 30-second calibration.

Tap inside the button area (the big red/grey rectangle, roughly 140×70 px at the top-left). Tapping anywhere else does nothing — by design, no accidental toggles from a brush against the edge of the screen.

Shot stages never show Screenshots aren't configured in flashair-sync's .env Set FLASHAIR_SHOT_DIR / LOCAL_SHOT_DIR / REMOTE_SHOT_DIR (all three or none)

Heater toggles on its own (ghost taps) Pressure threshold too low — noise triggering taps Raise TOUCH_PRESSURE_THRESHOLD in .env (default 150; try 250).
"touch init failed: No such file or directory" SPI not enabled, or /dev/spidev0.1 missing Confirm dtparam=spi=on in /boot/firmware/config.txt; ls /dev/spidev* should show both spidev0.0 and spidev0.1.

What the FlashAir line means

The daemon writes one of seven stages to /run/heater-flashair.json. Each renders distinctly so you can see exactly which phase the Pi is in:

StageWhat's happeningSSID shown
scanning cardConnected to the FlashAir, enumerating filesFlashAir SSID (amber)
downloading N of M logsCSV files coming off the cardFlashAir SSID (amber)
downloading N of M shotsBMP screenshots coming off the cardFlashAir SSID (amber)
uploading N of M logsCSVs being SCPed to the remoteHangar SSID (grey)
uploading N of M shotsBMPs being SCPed to the remoteHangar SSID (grey)
done — N logs + M shots, X agoJust finished, < 10 min (green)Hangar SSID (grey)
idle — last sync N logs + M shots, X agoSteady state, > 10 min since last work (dim)Hangar SSID (grey)

During the two download stages the sub-line shows "N shots queued" or "N logs done" — that's the other pipeline's status, so you know at a glance whether *all* the work is finished or only the CSV half.
