Hangar motion-wake backlight — install

Adds a DFRobot C4001 (SEN0610) 24 GHz mmWave sensor so the 3.5" dashboard's backlight sleeps when the hangar's empty and wakes on motion. Assumes the display is already installed and running. Check off each step — progress is saved in this browser.

Why bother: the IPS panel has no burn-in, so this is purely about LED-backlight hours + heat on an always-on display. The feature is opt-in (PRESENCE_ENABLED=1) and fail-safe — an unwired or dead sensor leaves the backlight on, never dark.

Parts check

Set the DIP switches — I2C mode + address

The C4001 talks I2C or UART, set by two DIP switches on the back of the board (not a slide switch — the silkscreen labels each one). We use I2C so the sensor shares the bus the touch chip already uses (no extra GPIO).

If i2cdetect later shows 2b instead of 2a, don't reopen the case — just set PRESENCE_I2C_ADDR=0x2B in .env and restart the display. The address switch isn't critical; the mode switch is.

Power down before wiring

Important: shut the Pi cleanly before touching the header. GPIO isn't hot-pluggable, and a one-pin slip shorts 3V3 → fry.

Wiring — sensor onto the I2C bus

The C4001 hangs on the same two I2C lines as the touch chip — wire it in parallel. Address 0x2A doesn't clash with the touch chip's 0x38. Pi Zero W 40-pin header; 3.3V logic and 3V3 power throughout.

C4001 pinPi BCMPi header pinNotes
+ (VCC)3V31 / 17Power. Both 3V3 pins are taken (DS18B20 on 1, panel on 17) — tap the breadboard 3V3 rail you already have.
− (GND)GND6 / 9 / 14 / …Any GND pin (or the breadboard GND rail).
D/T (SDA)BCM 23Data line. Shared with the FT6336U touch — wire in parallel onto the same line.
C/R (SCL)BCM 35Clock line. Shared with touch.
The board prints + − C/R D/T, not SDA/SCL. In I2C mode D/T is data (SDA) and C/R is clock (SCL) — the same two pins double as UART TX/RX when the mode switch is on UART. It's a 4-pin Gravity connector: there's no separate OUT/IO pin to leave unconnected. Power it at 3.3V, not 5V (the board accepts either) so its logic stays Pi-safe.

Wiring — move the backlight to GPIO18

The panel's LED/backlight pin is currently jumpered to the 3V3 rail (always on). Move that jumper's Pi end to GPIO18 so software can switch it.

Panel pinFromTo (Pi BCM)Pi header pin
LED / BL3V3 railBCM 1812
Drive test first — does the LED pin need a transistor? A GPIO can source only ~16 mA. Two ways to check before committing:
  1. Measure: multimeter in series on the old VCC→LED jumper, powered on. < ~16 mA → GPIO drives it directly (it's a logic-level enable). More than that → it needs a transistor.
  2. Observe: after wiring to GPIO18, run the on/off test (below). Full brightness when on → direct drive is fine. Noticeably dim → too much current for the GPIO.
If it needs a transistor: a logic-level N-MOSFET (2N7000 / AO3400) low-side on the backlight's ground return — gate ← GPIO18 (100 Ω in series), source ← GND, drain ← the LED/return pin, 10 kΩ gate→GND pulldown. PWM on the gate then dims as normal.

Confirm both chips on the bus

I2C is already enabled (the touch chip uses it) — no raspi-config needed.

Install the sensor library

Aim & tune

The mmWave beam is a forward lobe — long down the centerline, wide up close. Point it down the length of the hangar. Use the live readout to confirm coverage and pick the mounting angle.

Default mode is motion (12 m, whole hangar). A motionless person reads as no-target — the rolling idle timeout bridges that. Switch to PRESENCE_MODE=presence for still-presence holding, but only to ~8 m.
Reading near-field phantoms, or detecting too eagerly? The C4001 ships fairly hot and a metal hangar throws multipath, so a near-field range that bounces around (e.g. < 2 m while you're 8–10 m off) is the sensor chewing on clutter, not tracking you. Tune it with opt-in .env knobs — unset = leave the sensor's own config alone — then re-run --presence-test; the presence: C4001 ready (… tuning: …) line echoes what took effect:
  • PRESENCE_RANGE_MIN_CM=150 — ignore returns closer than 1.5 m (kills near-field clutter)
  • PRESENCE_RANGE_MAX_CM=1200 — cap reach at your real coverage (240–2000 cm)
  • PRESENCE_TRIG_SENS=4 — trigger sensitivity 0–9; lower = fewer false wakes
  • PRESENCE_FRETTING=off — ignore micro-motion (breathing-scale jitter), fewer phantoms
These persist to the sensor's own flash, so they survive reboots once written. Only detected drives the backlight — a wrong range won't break motion-wake, but phantom detected: True with nobody there keeps the screen awake, which is what these dial out.

Troubleshooting cheat-sheet

SymptomLikely causeFix
Screen never sleeps Sensor unavailable → fail-safe-on, or constant detections Journal: presence: … unavailable means lib/wiring. Otherwise something's moving in-beam (HVAC airflow?) — narrow the aim.
Screen never wakes Sensor reading but mis-aimed, or backlight not switching --presence-test to confirm detection; then check the LED pin actually moved to GPIO18 and the drive test passed.
2a missing from i2cdetect SDA/SCL swapped, mode switch on UART, or no power Re-check pins 3/5, set the board to I2C, confirm 3V3 on VCC.
Backlight dim, not full LED pin sources more than a GPIO can drive Add the N-MOSFET (see the drive-test note).
presence: DFRobot_C4001 lib unavailable Library file missing, or its pyserial/smbus deps aren't installed (the message names the missing one, e.g. No module named 'serial') Copy DFRobot_C4001.py into /usr/lib/cgi-bin/remote-switch/, and install the deps: sudo apt-get install -y python3-serial python3-smbus.
Wakes/sleeps too eagerly Timeout too short, or beam catching the apron through an open door Raise IDLE_TIMEOUT_SECS; aim away from the door line.
Tapping a dark screen toggles the heater Running an old display_loop.py without tap-to-wake git pull the branch with this feature, restart display.
Heater toggle / display dies after enabling — Set PRESENCE_ENABLED unset and restart: the feature is fully opt-in, so this isolates it instantly.
